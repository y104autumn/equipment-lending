# 要件定義書 — 備品貸出申請（2026-10-21）

⛔ 題材は架空の社内業務。実在の会社の業務は使わない。
目的: 画面設計（Figma）→ 実装（Claude Code）→ 業務フロー、の流れを 1 本通す業務の模擬。

## 1. 業務

社員がノート PC・モニターなどの備品を借りる時に申請し、総務が承認して貸し出し、返却を記録する。
業務の流れは `業務フロー図.md`。

## 2. 登場人物

| 役割 | すること |
|---|---|
| 申請者（社員） | 備品・期間・理由を入れて申請する |
| 総務（承認者） | 申請を承認または却下する。承認したものを貸し出し、返却を記録する |

## 3. 状態

| 今の状態 | 操作 | 次の状態 |
|---|---|---|
| 申請中 | 承認 | 承認済 |
| 申請中 | 却下 | 却下（終了） |
| 承認済 | 貸出 | 貸出中 |
| 貸出中 | 返却 | 返却済（終了） |

⛔ 表に無い操作はサーバーが拒否する（例: 申請中から返却はできない）。

## 4. 画面（1 画面）

| 区画 | 項目 |
|---|---|
| 申請フォーム | 申請者名・備品（ノート PC／モニター／プロジェクター／会議用マイク）・開始日・返却予定日・理由・「申請する」 |
| 申請一覧 | 申請番号・申請者・備品・期間・状態・操作ボタン（状態に応じて 承認／却下／貸出／返却） |
| 絞り込み | 状態で絞る |

## 5. 入力の決まり

- 申請者名・備品・開始日・返却予定日は必須。理由は任意（200 字まで）。
- 返却予定日は開始日以降。
- 入力の検査は画面とサーバーの両方で行う（画面を通らない呼び出しもサーバーが止める）。

## 6. 構成

| 層 | 技術 |
|---|---|
| 画面設計 | Figma（Claude Code から MCP で作成） |
| フロントエンド | React＋TypeScript（Vite）＝`frontend/` |
| サーバー | Spring Boot（Java 21・Maven）＝`backend/` |
| データ | PostgreSQL（このアプリ専用の DB `equipment_lending`）。表は `docs/04_契約/テーブル定義書.md` |

## 7. API

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/api/equipment` | 備品の一覧（申請画面の選択肢） |
| GET | `/api/requests?status=<状態>` | 一覧（状態は省略可） |
| POST | `/api/requests` | 申請する |
| POST | `/api/requests/{id}/approve` | 承認 |
| POST | `/api/requests/{id}/reject` | 却下 |
| POST | `/api/requests/{id}/lend` | 貸出 |
| POST | `/api/requests/{id}/return` | 返却 |
| POST | `/api/requests/{id}/ai-check` | Dify に申請の確認ポイントを聞く（状態は変えない・結果は保存しない）。Dify が使えなくても 200 で「取得できない」を返す。呼び方は `docs/04_契約/Dify連携.md` §2.2 |

| 応答 | いつ |
|---|---|
| 400 | 入力の決まり（§5）に反する |
| 404 | 申請番号が無い |
| 409 | 状態の表（§3）に無い操作。または同じ申請を同時に操作した時の後の方 |

申請の応答には `actions`（今の状態で押せる操作の一覧。例 `["approve","reject"]`）を入れる。画面はこれだけを見てボタンを出し、状態の表を画面側に持たない。
